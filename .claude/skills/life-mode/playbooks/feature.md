# Feature

New or changed gameplay behavior. The order is fixed: **design, scaffold, look, place, build, test, look, review, ship.** Each step has a cheap check; do not start the next one on a red check. `tools\cli feature new` writes `tmp/feature-<name>.md`, the same list as tick boxes for the kind you picked.

1. **Design: one paragraph before any code.** Name the consumer, the data shape, and the boundaries. Who calls this, from which side (server or client), on which entity? What owns the behavior (a prefab, a component on an existing prefab, a manager singleton)? What config drives it? Then mark each boundary: replication (what the server owns, what the client sees), config (what is data), persistence (what survives a restart, and which payload carries it), UI (client-only, calls the server). Say how it is in-world first: the object the player walks up to, and why a sheet is needed if one is (`docs/decisions.md`). That paragraph goes in `Feature.md` and is the spec. If you cannot name a concrete caller, the design is a library without a user.
2. **Research.** Base game first, with **enfusion-api-research**: `component_search` for the component to attach, `api_search` for the methods to override, `game_read` on the vanilla class you extend. Reuse the base game's systems (inventory, damage, vehicles) before building your own. Then read one sibling feature under `Scripts/Game/Feature/<Area>/` for the mod's shape. Subtract before you add: finish or delete a half-built stub in the path, do not build around it (**principles**).
3. **Scaffold.** `tools\cli feature new <Area> <Name> --kind logic|world|ui|item --issue <n>`. It writes the script skeleton, the tests with their red-proof slots, the session proof, the string rows, the `Feature.md` section, the `features.md` and `playtest.md` lines, the `ResetStatics` call and `tmp/pr-body-<slug>.md`, all in the shapes the validators check. Every gap is marked `TODO(scaffold)`; `tools\cli feature check` lists the ones left. Do not hand-write these files.
4. **Look before** (anything a player sees). `tools\cli look <area>`, read the sheet, `tools\cli evidence <issue> before <area>`. You are fitting a new thing into this scene; pick its place and its prop from `docs/style-guide.md` now, not after the code works.
5. **Place.** `tools\cli place on|against|ground|arrange`, then `tools\cli audit placement --area <area> --strict`. A new world interactable also runs `node tools/actions/place-action-contexts.mjs`. Follow **enfusion-resource-authoring**.
6. **Build the smallest working slice end to end**: one prefab, one component, one config, wired with the string keys, following **enfusion-script-authoring**. Every refusal logs through `LF_Debug`. `tools\cli validate` after each step (45 s).
7. **Test, red first and observed.** `tools\cli test --no-build --only LF_Test_<Name>` (about 10 s): break one assertion, paste the observed `[LFTEST] FAIL` line into `// red-proof:`, restore it. `validate-tests` refuses the scaffold's `PENDING`. Then the WORLD test the same way. `--tier all` once, at the end. Persistence, replication and late join need their proof class (**enfusion-verify**).
8. **Look after.** `tools\cli look <area>` again, open the close-ups, and walk the **polish** checklist against the pictures. Fix and re-look until it holds; `tools\cli evidence <issue> after <area>`. `look`, `look item <prefab>` and `wb_preview` are the PR pictures for placement, props, signs, items, prefabs, materials and layers. Open one `--profile full` session only for what Workbench play cannot capture (a sheet or HUD, a second player or late joiner, motion, animation, sound): run the session proof in it, keep its shots, `session down`.
9. **Review.** When the diff touches replication, an RPC, persistence, money, inventory, or resource GUIDs, run **interrogate** before shipping: it found a real defect in five of the seven feature PRs that used it. The reviewer writes its findings to `tmp/review-<slug>.md`; you tick each one `fixed: <what>` or `dismissed: <why>` and re-run the affected test. A pure logic or dressing change skips this and says so in the PR's `## Review` section. Check **enfusion-blast-radius** when you edited a base prefab, a shared component or an RPC signature.
10. **Ship.** Fill `tmp/pr-body-<slug>.md`, delete scaffolding and debug logging, then `tools\cli wt ship <slug> --refs <n> --body-file tmp/pr-body-<slug>.md`. Ship checks the body before the gate: a body file for any `addons/` change, no `TODO(scaffold)`, a `## Manual testing` section, an embedded picture for a player-visible change, and no open review finding. The review file is appended to the PR by ship. Near your tool-call budget with the tests green, ship now and put the unreached checks under `## Manual testing` (`docs/agent-budget.md`); do not polish past it.

**Reply:** the data shape, what a player now sees (embed the after picture), how you verified it, what stays manual, and the last line `agent-scope` asks for. "Merged, in-dev", never "done".
