## Findings

1. **`jip-sweep-proof` failed one row the first time, in a used session; part 2 re-ran it in a reused session and it
   failed the jail row again, for a cause that is now known.** First run: the characters had been used by the ten hours
   of proofs; `NOTE A is not serving a sentence` and `SUMMARY jip-sweep-proof fail rows=22 failed=1`, the failed row
   `jail sentence running`. All 21 other rows passed. Rerun in a fresh two-client session: `ok rows=22 failed=0`.
   **Why (read from the two logs):**
   - *RC run (`ws/slice-4836`, `jip-sweep-proof-20261128-084516.log`).* B cuffed A and the booking desk opened and was
     signed (`ok LF_BookingDeskBookAction`, charge sheet checked and signed), so the setup was fine. The failing step is
     A's "Take the time" answer: every `aim` of client 1 in the answer loop reads `camera=SCR_ManualCamera pitch=-27
     hit=none`, whatever pitch the proof sets (-45 to -10), so the aim never selects `LF_BookingDeskAnswerAction`, the
     proof presses `confirm` at nothing and A stays cuffed in the cell with `jail=0`. The fresh run reads
     `camera=PlayerCamera ... selected=LF_BookingDeskAnswerAction`, pitch -45 first try, `jail=893 s`. So client 1's view
     was a scripted camera (`SCR_ManualCamera` is what the dialogue and film cameras use) left on by something earlier in
     that long session. **Which earlier step left it was not found**; in part 2 client 1 read `PlayerCamera` throughout,
     so it did not reproduce, and no player-facing fault is shown (a harness client's camera, not a player's report).
   - *Part 2 re-run (session G: `up --clients 2 --roster 1`, `booking-desk-proof`, then `jip-sweep-proof`,
     `jip-sweep-proof-20261128-101807.log`):* `SUMMARY jip-sweep-proof fail rows=22 failed=11` (`failures=33` are retried
     verbs), the same `jail sentence running` row among them, and now a different cause. `booking-desk-proof` had jailed B
     (client 2) and a booking-desk sentence is 900 s: when the sweep started, B's state read `jail=781`, so B's police
     application and clock-in did nothing (`faction=CIVILIAN duty=0`), `hold Handcuffs -> not_carried`, A was never cuffed
     (`A cuffed on the server: 0`), `use LF_BookingDeskBookAction -> error cannot_show`, and A never had a sentence
     (`jail=0`). The other ten failed rows (`vehicle plate`, `house owned`, the door, crew and shelf rows) are most likely
     the same cause: the "there all along" reads are taken on client 2, and B was locked in a cell that read the world
     from the wrong place (not checked row by row).

   police and jail state, not because the late joiner reads a wrong replica; both failing runs had a different
   leftover (a camera on A, a running sentence on B). `jip-sweep-proof` is a fresh-session proof: run it **last, in its
   own two-client session, `up --mission island --clients 2` without `--roster`**, as the run order already says. A
