# Map review, 2026-11-17

Deep adversarial review of the modded map, epic #2223: POIs, areas, waypoint, personal and org marks, discovery, shares, dispatch, job and event marks, the legend, the marker-provider API and its visibility, and the 128-player perf gate. It covers the whole feature, not a diff. Two passes were made: one on persistence, sync, rate limits, static resets and per-frame cost, and an independent one on visibility leaks, client trust and RPC direction. Both passes found findings 1, 2 and 4 on their own.

Files: `Feature/Map/*.c`, `Comms/LF_ServiceCallMapMarks.c`, `Events/LF_EventMapShare.c`, `Jobs/LF_JobMapMarks.c`, `Organizations/LF_OrgMapMarks.c`, `TownBoard/LF_TownBoardMapKnown.c`, the map payloads in `LF_PersistenceComponentSerializer.c`, and vanilla `SCR_MapMarkerBase.c` / `SCR_MapMarkerManagerComponent.c` from the game paks.

**Result:** 5 confirmed (4 fixed in this PR, 1 filed), 9 plausible (filed), 6 dismissed. Issues: #2492, #2493, #2495.

## Confirmed

### 1. Shared marks were counted, uploaded and saved as personal marks (fixed)
`LF_MapMarksSync.c:92` `IsPersonal`, used by the cap at `:45`, the upload at `:185` and the restore.
- `LF_MapShareComponent.c:127` inserts every shared row (dispatch, org, job, event) as a local `PLACED_CUSTOM` marker. A local marker keeps vanilla's `m_iMarkerID = -1` (`SCR_MapMarkerBase.c`), so it passed both personal tests: type and id -1.
- **Scenario A (leak):** a member's org marks its hideout. The member's client uploads that mark 2 s later as one of their own personal marks and the server saves it under `mapmarks`. After a kick from the org, the mark is restored on every spawn as an editable personal mark, across restarts. An officer who clocks out keeps old caller positions the same way.
- **Scenario B (lost dispatch):** an officer with 20 personal marks gets a call. The insert hits the 20 cap and returns, so the call never shows, while `LF_MapShareComponent.m_mMarkers` believes it does.
- **Scenario C:** `Restore` on respawn removed live shared markers, because they counted as personal.
- **Fix:** shared marks set `CanBeRemovedByOwner(false)` before their insert, and `IsPersonal` now returns false for a read-only marker. Test `LF_Test_MapShareNotPersonal` (LOGIC, RED-OK: "expected 1, got 3").
- **Left over:** copies already saved in `mapmarks` come back as ordinary deletable marks (#2495).

### 2. Job and taxi marks never reached an account's first character (fixed)
`LF_MapShares.c:107` `LF_MapShareGameFacts.MemberOf` (was inline in `Of`).
- `LF_JobAction` puts the `PLAYER` row under `LF_Utils.GetPlayerUid`, the character record key. For slot 1 that key is the account uid (`LF_PlayerAccount.AddCharacter`).
- The share table's member used `character.GetId()`, a generated id. They never matched, so on the first character (most players) the stop mark, the waypoint (`LF_JobWaypointRplSink.Channel`) and the spawn resend (`ResendFor`) all found nobody.
- The tests used fixture facts with matching strings, so they could not see it. This is the mirror image of the org-mark bug fixed in the property review.
- **Fix:** `m_sUid` is the record key, and the org is still looked up by character id. Test `LF_Test_MapShareMemberKey` (LOGIC, RED-OK) drives the real `MemberOf` with a real account.

### 3. ROLE places never showed (fixed)
`LF_MapPois.c:42/54`, callers `LF_MapPlacesUI.c:430` and `LF_MapPlacesKnown.c:238`.
- Neither client audience builder called `AddRole`, so a `ROLE` kind (the core `PoliceArmoury` row) was hidden even from on-duty police. The emulator's `--as police` already showed it, so the game had drifted from its twin.
- **Fix:** `LF_MapPoiAudience.Local()` adds roles from the replicated account state (`AddRolesFromState`). `PollKnown` picks up a duty change because the visible set's signature changes.
- Test `LF_Test_MapPoiRoleAudience` (LOGIC, RED-OK).
- No world places a `PoliceArmoury` yet, so there is nothing to photograph.

### 4. Personal-mark sync and save shared the COMMS rate bucket (fixed)
`LF_MapMarksSync.c:286/297`.
- The bucket allows 3 requests per 5 s and is shared with phone dial, pick-up and the service board.
- **Scenario:** a player dials, picks up and reads the board, then respawns. The restore is refused and the map comes up empty. The next edit uploads one mark, and `LF_MapMarks.SetCharacter` replaces the 20 saved marks with it.
- The same bug was fixed for the discovery sync on 2026-11-17 (`LF_MapKnownSync`) but not here.
- **Fix:** an own bucket, `LF_ERequestKind.MAP` (4 per 5 s), through `LF_MapMarks.AllowAsk`. Test `LF_Test_MapMarksRateBucket` (LOGIC, RED-OK).

### 5. Hidden and underworld places are known to every client (filed #2492)
`Core/LF_Places.c:23` registers every place on every machine, and the map's POI layer and the discovery scan filter on the client.
- A script-modded client can draw every `HIDDEN` place, such as the pack's `Fence`. The server decides only for shares.
- Fixing it is a design change: send positions with knowledge, and keep private places off clients. Too large for this PR.

## Plausible

6. **The perf gate misses the 5 s share sweep** (#2493). `perf/map-128` times one `Put`. The steady cost is `RefreshAll`: 128 players times every row in one frame, plus one real `Of()` per player. It is not measured.
7. **The over-cap warning repeats every sweep** (#2493). `WantedFor` warns each sweep for every player over 64 rows. A log flood, not a gameplay bug.
8. **A character switch inside the 2 s upload window** saves the old character's marks under the new key (#2495).
9. **Shared-mark copies already in saves** (see finding 1) come back as editable personal marks (#2495).
10. **A dispatch mark outlives a resolved call.** It is removed only on expiry or world reset, and there is no close event (#2495). The audience is still correct.
11. **Org mark icon and colour are only bounded to 0..255** and positions to int16. Vanilla bounds-checks the index, so there is no crash, but a rank holder can fill the 20 slots with invisible or off-map marks (#2495).
12. **`LF_MapPoiKind.m_eVisibility` defaults to `PUBLIC`.** A pack row that leaves it out makes its kind visible to everyone (#2495). All shipped rows set it.
13. **Medic clock-out waits up to 5 s for the sweep**, while police refresh at once (#2493).
14. **`LF_MapKnown.s_mAsks` keeps one small array per player id that ever asked** and never prunes it. That is a few ints per player per session and is cleared at world end. Noted, not filed.

## Dismissed

- **RPC direction and ownership.** Every `RpcAsk_*` is `RplRcver.Server` on the asker's own controller and takes identity from `GetPlayerId()`/`GetOwner()`, never from the payload. Every `RpcDo_*` is `RplRcver.Owner` with a host shortcut. Nothing is broadcast, there is no `RplProp`/`RplSave` in the map, and no `EntityID` goes on the wire.
- **Personal-mark payload trust.** The flood is refused before parsing (more than 40 rows), the shape is checked, text is cut to 64 characters, and the cap is enforced on the server. Icon and colour indexes come back only to the same client, so a bad value harms only the sender.
- **Org mark asks.** Membership, the `MANAGE_TERRITORY` right, the 20 cap, a 2 s rate per character, `#` stripping and the 32-character text cap are all checked on the server. Serials are never reused in a session.
- **Persistence.** `mapknown`, `mapmarks` and `orgmarks` are appended in order (save versions 42, 43, 44). Each `ApplyAll` replaces its store, so load is idempotent. Rows carry their own `m_iVersion`. A failed read degrades only that payload.
- **Static resets.** Every map class with statics has an `LF_StaticResetHook`. The cached POI and area configs are resources and do not need one. The sweep and scan call queues are removed on reset.
- **Taxi fare marks have no caller.** This is documented as waiting for the fare system (M6, `docs/features/map.md`), not dead by accident.
