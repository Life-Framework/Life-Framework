# Organisations review, 2026-11-17

An adversarial review of organisations and gangs across the whole feature, not only recent diffs. It covered `Feature/Organizations` (registry, ranks and rights, invites, the ledger and its requests, org map marks, the playtest sign, config) and `Feature/Hideouts` (lease, gate, stash, processing, held ground). It also read open PR #2522, which registers the lease as `org_base` in `LF_Places`. The review hunted for listen-host and dedicated-server gaps, client trust, persistence order, exploits (dupes, free money, rank escalation, griefing) and unwired features.

How it ran (the `interrogate` skill): I read the registry, the money boundary, the ledger RPCs, the rules and rights, and the invites and lease. A separate read-only Opus reviewer took the hideouts, map marks, replication, the rank and invite roles, the playtest sign and PR #2522. I re-read each of its findings in the code before marking it. This review overlaps the property review from earlier today (`2026-11-17-property.md`, organisation leftovers in #2415). Where a finding repeats one of those, this review points to it and does not file it again.

**Result:** 8 confirmed: 5 fixed in this PR with red-proof tests, 2 filed as #2533, and 1 already tracked in #2415. 2 plausible: 1 filed in #2533, 1 already in #2415. 14 dismissed.

## Fixed in this PR

### 1. The ledger did nothing for a listen host (confirmed, #2525)

**Where:** `Organizations/LF_OrganizationCharacter.c`. The seven `LF_AskOrganization*` methods and `LF_PushOrganizationView`.

**Scenario:** a listen host is the server, so its own `Rpc(RpcAsk_...)` never reaches the handler. The host could not view, found, deposit, withdraw, buy, lease or leave. The reply `Rpc(RpcDo_LF_OrganizationLedger)` targets the owner, and on a listen host the owner of the host's character is the server itself, so the page never updated either.

**Fix:** each ask calls its handler directly when `Replication.IsServer()`. The reply applies the page directly when the server owns the character (`RplComponent.IsOwner`, the same as `LF_CharacterATMComponent.ReplyResult`). A dedicated server owns no player's character, so it still replies over the wire. The seven entries are gone from `tools/validation/rpc-host-path-baseline.json`.

**Proof:** `validate-rpc-host-path` with the entries removed fails the unfixed file with 7 problems and passes the fixed one. A listen-host ledger session is in the manual steps.

### 2. The ledger sold upgrades that do nothing (confirmed)

**Where:** `Organizations/LF_Organization.c`, `LF_OrganizationManager.BuyUpgrade`. `RpcAsk_LF_OrganizationBuy` accepts any of the three ids.

**Scenario:** the ledger offers only the processing slot. A client that sends `EXTRA_STORAGE` (0) or `PARKED_VEHICLE` (2) is charged 500 or 750 from the fund and gets a saved flag that no system reads (`HasExtraStorage` and `HasParkedVehicle` have no caller). A member with the buy right can drain the shared fund on nothing.

**Fix:** `IsUpgradeWired` allows only the processing slot. The other two are refused with a warning and charge nothing. Prices and flags stay, so wiring them later is one line.

**Test:** `LF_Test_OrgUpgradeUnwired` (`organization/upgrade-unwired`, LOGIC). It is red on the unfixed code: "extra storage, which nothing reads, is not sold".

### 3. The fund wrapped negative past int.MAX (confirmed, low)

**Where:** `LF_OrganizationManager.Deposit` → `LF_Organization.Credit`.

**Scenario:** each deposit is capped at `MaxCashMove` (1,000,000), but the fund had no ceiling. Once it neared 2^31 - 1, the next deposit wrapped it to about -2.1 billion: the player's cash was taken and the fund was lost. Reaching that needs a lot of money, so the severity is low, but the result is the whole treasury gone.

**Fix:** `Deposit` refuses an amount that would pass `int.MAX`. `DepositCash` already returns the cash on a refused credit.

**Test:** `LF_Test_OrgFundOverflow` (`organization/fund-overflow`, LOGIC). It is red on the unfixed code: "the fund did not wrap (expected 2147483637, got -2147483559)".

### 4. The stash ignored the rank's stash right (confirmed)

**Where:** `Hideouts/LF_Hideout.c`, `AllowsStash`.

**Scenario:** `USE_STASH` is a saved rights bit. The owner's rank config can take it off a rank (`LF_OrgConfig`), and the catalogue names it. Yet `AllowsStash` checked membership only. An owner who took the stash off the member rung still had every member opening, emptying and filling the stash. All three stash paths (open, take, put) go through `AllowsStash`.

**Fix:** after the membership check, `AllowsStash` requires `org.Allows(characterId, USE_STASH)`. Every shipped rung and every migrated rank already has the right, so default play is unchanged.

**Test:** `LF_Test_HideoutStashRight` (`hideout/stash-right`, LOGIC). It is red on the unfixed code: "a rank without the stash right is refused".

### 5. A gate saved open stayed open after a restart (confirmed)

**Where:** `Hideouts/LF_Hideout.c`, `ApplyAll`.

**Scenario:** the save keeps the gate's lock state. A member opens the gate, and the server saves before the 15 s relock sweep (or while the member stands within 40 m). After the restart the gate loads open. Only `TryUnlock` started the sweep, so the gate stayed open for anyone until a member next used it.

**Fix:** a load with any leased gate open queues the relock sweep, which shuts the gate once no member is near. The open state still loads as saved, so the existing restart tests (`e2e/...` "the held site keeps its open lock") hold.

**Test:** `LF_Test_HideoutLoadRelock` (`hideout/load-relock`, LOGIC). It is red on the unfixed code: "a load with the gate open queues the relock sweep". The test reads the new `LF_Hideout.IsRelockScheduled()`.

Green run: the four new tests plus `org/rights`, `org/rights-persist`, `org/registry`, `hideout/relock-and-load`, `hideout/stash`, the hideout and organisation roadmap tests, the held-ground round trip and legacy load, the test sign and the invite role. 20 passed in both legs.

## Manual testing

1. Listen host (Workbench play or `-server` with a local client as host): walk to the registry desk and open the ledger. Expect the page to show the organisation state. Found an organisation, deposit, withdraw, buy the processing slot, take the lease. Each action updates the page and shows its notice line. Before this PR the host's ledger never answered.
2. Dedicated server, one client: repeat step 1 and expect the same result (the wire path is unchanged).
3. Restart: as a member, unlock the hideout gate, save at once, and restart the server. Join as a non-member and wait 15 s at a distance. Expect the gate to lock (log `door relocked hideout=... no member is near it`).
