# The Everon map (epic #2223)

Design: `docs/architecture/everon-map.md`. One row per card; each card appends its own.

- ✅ **POI data (#2230, M2):** a point of interest is a live `LF_Places` entry whose kind has a row in the POI table. `Configs/Map/LF_MapPois.conf` (`LF_MapPoiConfig`, one `LF_MapPoiKind` row per kind: category, icon, label key, min zoom, visibility `PUBLIC`/`DISCOVER`/`HIDDEN`/`ROLE`, role) ships neutral rows; the pack overlays it by kind through `LF_ConfigOverlay` (`LF_Everon1989/Configs/Map/LF_MapPois_Everon1989.conf`, listed in the mission header, adds the hidden `Fence` kind). `LF_MapPois.CollectLive(audience, out)` reads `LF_Places` on any machine and applies the visibility rule (`LF_MapPoiRules.Resolve`) for an audience (`LF_MapPoiAudience`: roles held and what the player knows of each place id). Result per place: `hidden`, `faded` (heard of), `full`, or `pencil` (a hidden place the player met, never public). A kind with no row never shows (a vault, a dispatch source). The rule is one case table, `Configs/Map/Rules/visibility.cases.json` (the loader format of `tools/map/rules/index.mjs`), run by `LF_Test_MapPois` (Enforce; the engine cannot open a loose addon `.json`, so it reads `LF_MapPoiCases.generated.c`, written by `node tools/map/rules/visibility.mjs --gen`) and by `tools/validation/map-visibility-selftest.mjs` (node twin `tools/map/rules/visibility.mjs`, which also exports the emulator's `visible(poi, persona)`), so they cannot drift. Not done: drawing the icons (M4), the per-player known set and its saving (M13), the role source (on-duty police and medic) fed into the audience.
- 🧪 **Discovery core (#2241, M13):** what each character knows of each place: unknown, heard of or visited (D-M4), per character only (D-M12), saved as the `mapknown` payload (save version 42) and kept across the 24 h reset. `LF_MapKnown` (`Feature/Map/LF_MapKnown.c`) is the server store. The owner's machine looks around every 2 s (`LF_MapKnownScan`, not from a vehicle above 60 km/h) and asks `RpcAsk_LF_MapDiscover(kind, placeId)` on its own controller for a `DISCOVER` place within 20 m it has not visited; the server checks the kind is a `DISCOVER` POI row, the place is live, its own view of the character is within 20 m plus 10 m slack, and 5 asks a minute, then records the visit and answers `RpcDo_LF_MapKnown`. The board, the clerk and quests call `LF_MapKnown.Hear(playerId, placeId)` (never lowers visited; works for a place not live yet). On join, respawn and character switch the owner pulls the character's whole set (`RpcAsk_LF_MapKnownSync`, answered by one owner RPC of ids and states; its own gate `LF_MapKnownSync.Admit`, one answer a second per player with a second ask inside it deferred, never the shared `COMMS` rate bucket, which dropped the sync after three chess moves or board reads); `LF_MapKnown.FillAudience` hands the local set to `LF_MapPois`. The rule is one case table, `Configs/Map/Rules/discovery.cases.json`, run by `LF_Test_MapKnown` (through `LF_MapKnownCases.generated.c`) and by `node tools/map/rules/discovery.mjs` (the node twin; `known(poi, persona)` for the emulator's `--as known`). Not done: a per-kind discovery radius on the POI row (the rule takes it), callers of `Hear` (board, clerk, quests), drawing (M4). Tests `map/known`, `map/known-persist`, `map/known-sync-gate`.
- 🧪 **Personal marks saved (#2236, M8):** vanilla shared markers are off (D-M7): a modded `SCR_MapMarkerSyncComponent` forces its placed-marker limit to 0 after `OnPostInit` (the server's `RPC_AskAddStaticMarker` adds nothing) and refuses the client ask, and a modded `SCR_MapMarkerManagerComponent.InsertStaticMarker` turns every player add into a local one (the dialog, the quick menu and a drag all end there; server markers pass). The placed-marker dialog offers the pencil set from `LF_MapIcons.imageset` (cross, circle, arrow, note, question; `Configs/Map/LF_MapMarkerConfig.conf`; saved marks keep the icon by index, so the list only grows at the end). Each character keeps up to 20 marks (D-M11; the client refuses the 21st, the server refuses it again), saved as the `mapmarks` payload (save version 43) and kept across the 24 h reset. The owner uploads its whole list 2 s after a change (`RpcAsk_LF_MapMarksSet`, flat ints and notes, checked for shape and cap) and on join, respawn and character switch pulls it back (`RpcAsk_LF_MapMarksSync` → `RpcDo_LF_MapMarksSync`), re-inserting the marks as local markers (`Feature/Map/LF_MapMarks.c`, `LF_MapMarksSync.c`). - ✅ **Emulator POIs from live places (follow-up to #2251):** `tools\cli map render` draws the POIs a persona would see from the same data the game uses. The POI table is per kind with no coordinates (rule 9), so `tools/map/lib/places.mjs` reads the `.layer` files of `--world` (`main` the pack island, the default; `town` the DebugWorld village plus the pack's Everon1989Town layers; `debug`; `grid`; or a layers folder or one `.layer`), follows prefab ancestry for components a prefab carries, and collects each place's kind, id, position and live state from `LF_PlaceComponent` and the feature components that register a POI kind (`LF_WorkplaceComponent`, `LF_HospitalTillComponent`, `LF_HospitalCabinetComponent`; add a row to `PLACE_SOURCES` when another registrar gets a POI row). `tools/map/lib/overlay.mjs` joins them to the kind rows (core `LF_MapPois.conf` then the pack's `LF_MapPois*.conf`, replaced by kind), `visible(poi, persona)` from `tools/map/rules/visibility.mjs` decides what shows, and a place whose live state the header does not list stays dark (`--live-states 1,2` overrides the header's `m_aLF_LiveStates`). A world other than `main` draws on a plain metre grid and fits the view to its places (`--place fit`; `--base everon` keeps the terrain). With no place carrying a POI kind (the pack island has none yet) the render says so on stderr and draws no POIs, `overlay=none`. The stand-in rows are only `--fixture` and the render selftest. Tested by `tools/validation/map-places-selftest.mjs` (fixture layer `tools/map/render/fixtures/places.fixture.layer`: three kinds across the personas, a dark place, a kind with no row, a prefab-inherited place, a group, a nested child). - ✅ **Session harness and `map-shots` (#2228, M0b):** the harness verb `map open|close|pan <x> <z> <zoom> [seconds]|status`, plus `map waypoint <x> <z>` (what a right-click does, `LF_MapWaypoint.SetFromMap`), `map mark <x> <z> [n]` (n personal marks through `InsertStaticMarker`, answering the count before and after, so the 21st refusal reads back) and `map probe` (the `-lfMapPlacesProbe` measurement on demand plus the mean frame ms since the map opened, sampled by `LF_MapPlacesUI.Update`) from the map proof pass (`Feature/Map/LF_MapHarness.c`, a `modded class LF_AgentHarnessVerbs`, client side). The harness `input` verb refuses `GadgetMap`, so `open` holds the carried paper map (`SCR_MapGadgetComponent`, the way `hold PaperMap_01_folded` does; with none carried it opens the same `MapMenu` the gadget opens) and `close` switches the gadget's map mode off. `pan` centres on world `x z` with `SCR_MapEntity.ZoomPanSmooth` at the emulator's zoom: the view is `map width / 2^zoom` metres across (the width comes from the map entity, no constant), so a `tools\cli map render --zoom N` picture and the game frame the same ground. The map takes a few frames to start up and a pan before then does nothing, so `status` (`open=1 ppu=.. min=.. max=.. cx=.. cz=.. view_m=..`) is the read-back. The proof `node agent-box/session.mjs map-shots [--out dir] [--place name] [--bbox x0,z0,x1,z1] [--zoom N]` (`agent-box/proofs/map-shots.mjs`) takes its views from the emulator's own `resolveView` (default: the island, Saint-Philippe, the square), pans until the real width is within 5% of the emulator's, photographs the UI and writes `<view>.png` and `<view>-emulator.png`. Final proofs only (one run at the end of a visual card, `up --mission everon --profile full`); iterate in the emulator and the LOGIC tests.
- ✅ **Share core (#2237, M9):** one server table, `LF_MapShares`, holds shared marks by the owning system's key (`LF_MapShareRow`: key, audience `PLAYER`/`ROLE`/`ORG`/`EVERYONE` and its id, x and z in metres, icon and colour indexes, text of at most 32 characters, expiry in world seconds or 0). `Put` sends a row to exactly its audience and takes it from players who held it but are outside a changed audience; `Remove` takes it from everyone who holds it. Audience resolution (`LF_MapShareRules.InAudience`): `PLAYER` is the active character id, `ROLE` is an on-duty service only (`police` to police on duty, `medic` to medics on duty, off duty sees nothing: D-M10), `ORG` the org id, and an empty id or unknown audience reaches nobody. Membership changes go through `Refresh(playerId)` (owners call it at once; a sweep every 5 s refreshes everyone and expires rows), which sends the diff: rows the player now belongs to and removals for the ones they left. `LF_OnPlayerSpawnedEvent` (late join or respawn) clears the client's shared marks and resends the full set; a player holds at most 64 rows. Delivery is `LF_MapShareComponent` on `PlayerControllerRoleplayMP.et`: `RpcDo_MapShareAdd/Remove/Clear` with `RplRcver.Owner` on the recipient's own controller, never broadcast and no entity id on the wire; the client inserts each row as a local vanilla static marker (`InsertStaticMarker(marker, true)`) the player cannot delete (D-M7: the vanilla networked marker path is not used). Rules are one case table, `Configs/Map/Rules/shares.cases.json`, run by `LF_Test_MapShares` (LOGIC, via `LF_MapShareCases.generated.c` from `node tools/map/rules/shares.mjs --gen`, plus a four-player fixture through the table with a recording sink) and by `tools/validation/map-shares-selftest.mjs` (node twin `tools/map/rules/shares.mjs`). Nothing is saved (owners re-issue rows; org marks are M12). Not done: the callers (dispatch M10, taxi and jobs M11, org marks M12, events M15) and the shared-mark icon config.
- 🧪 **Org marks (#2240, M12):** a member whose rank holds the `MANAGE_TERRITORY` right (founders have it; a founder gives it to officers through the rank rights) places a mark for the whole organization, at most 20 per organization (D-M11). `LF_OrgMapMarks` (`Feature/Organizations/LF_OrgMapMarks.c`) is the server store; each mark is an `ORG <orgId>` row of `LF_MapShares` keyed `org:<orgId>:<serial>`, so members get it and nobody else does. The client asks on its own controller with `LF_MapShareComponent.AskOrgMark(x, z, icon, colour, text)` (`RpcAsk_OrgMark`) or `AskOrgMarkRemove(key)`; the server checks the organization, the right, the cap, one add per 2 s per character, int16 positions and u8 icon and colour, and trims the text to 32 characters (no profanity filter yet). Serials are never reused in a session (a per-org high-water mark), leading `#` is stripped so player text is never a string table key. A load keeps the marks of an organization that is not registered at that moment (a whole-store re-apply may run mid-swap); a future disband path must remove its org's marks. Saved as the `orgmarks` payload (save version 44), kept across the 24 h reset; a load re-puts every mark into the share table and skips rows with no org, repeated keys and rows past the cap. Joining or leaving an organization (create, invite, kick, leave) calls `LF_MapShares.Refresh` for that player at once (`LF_OrgMapMarks.RefreshCharacter`). This is how an org shares an underworld place by hand (D-M5). Org marks are put at load, so they take up to 20 of a player's 64 share slots ahead of later rows. Not done: the map UI to place and remove org marks (the asks exist; the dialog is M8's), the shared-mark icon config, officers holding the right by default. Test `map/org-marks` (PERSISTENCE). **Fixed (2026-11-17 property review, LOGIC `map/org-marks-character-id`):** the asks and `RefreshCharacter` resolved the player with `LF_Utils.GetPlayerUID`, the record key, which for an account's first character is the account uid; organizations list members by character id, so that character's every add and remove was refused. They now use `LF_OrgMapMarks.CharacterIdOfPlayer` (the active character's id).
