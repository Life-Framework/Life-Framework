# The Everon map (epic #2223)

Design: `docs/architecture/everon-map.md`. One row per card; each card appends its own.

- ✅ **POI data (#2230, M2):** a point of interest is a live `LF_Places` entry whose kind has a row in the POI table. `Configs/Map/LF_MapPois.conf` (`LF_MapPoiConfig`, one `LF_MapPoiKind` row per kind: category, icon, label key, min zoom, visibility `PUBLIC`/`DISCOVER`/`HIDDEN`/`ROLE`, role) ships neutral rows; the pack overlays it by kind through `LF_ConfigOverlay` (`LF_Everon1989/Configs/Map/LF_MapPois_Everon1989.conf`, listed in the mission header, adds the hidden `Fence` kind). `LF_MapPois.CollectLive(audience, out)` reads `LF_Places` on any machine and applies the visibility rule (`LF_MapPoiRules.Resolve`) for an audience (`LF_MapPoiAudience`: roles held and what the player knows of each place id). Result per place: `hidden`, `faded` (heard of), `full`, or `pencil` (a hidden place the player met, never public). A kind with no row never shows (a vault, a dispatch source). The rule is one case table, `Configs/Map/Rules/visibility.cases.json` (the loader format of `tools/map/rules/index.mjs`), run by `LF_Test_MapPois` (Enforce; the engine cannot open a loose addon `.json`, so it reads `LF_MapPoiCases.generated.c`, written by `node tools/map/rules/visibility.mjs --gen`) and by `tools/validation/map-visibility-selftest.mjs` (node twin `tools/map/rules/visibility.mjs`, which also exports the emulator's `visible(poi, persona)`), so they cannot drift. Not done: drawing the icons (M4), the per-player known set and its saving (M13), the role source (on-duty police and medic) fed into the audience.
- ✅ **Map plumbing (#2229, M1):** the Roleplay game mode (`GameMode_Roleplay.et`) now carries `SCR_MapConfigComponent` (gadget config `Configs/Map/LF_MapFullscreen.conf`) and `SCR_MapMarkerManagerComponent` (marker config `Configs/Map/LF_MapMarkerConfig.conf`), the two components vanilla's `GameMode_Base.et` has and ours lacked: without them the map menu returned before setup and no marker showed. `LF_MapFullscreen.conf` is a copy of vanilla's `MapFullscreen.conf` (an inherited array cannot drop items; a child config only adds) that keeps vanilla's layers, props, cursor module, descriptor visibility (town names and roads) and the map tools, markers, pencil, compass, ruler, watch, weather, light and radial, and drops the Conflict UI (`SCR_MapCampaignUI`), task list, journal (needs the task list and briefing) and military debug icons. `LF_MapMarkerConfig.conf` is vanilla's marker set (text, placed, military) without the dynamic squad-leader and air-support entries: their `InitServerLogic` reads `SCR_GroupsManagerComponent`, which this game mode has not, and crashed the manager's `EOnInit`. Test `LF_Test_MapConfig` (WORLD). Not done: the in-game picture of the open map (card M0b's `map-shots` proof is still owed), a `SCR_MapMarkerEntryMilitary` menu check in a live session.
- ✅ **Emulator POIs from live places (follow-up to #2251):** `tools\cli map render` draws the POIs a persona would see from the same data the game uses. The POI table is per kind with no coordinates (rule 9), so `tools/map/lib/places.mjs` reads the `.layer` files of `--world` (`main` the pack island, the default; `town` the DebugWorld village plus the pack's Everon1989Town layers; `debug`; `grid`; or a layers folder or one `.layer`), follows prefab ancestry for components a prefab carries, and collects each place's kind, id, position and live state from `LF_PlaceComponent` and the feature components that register a POI kind (`LF_WorkplaceComponent`, `LF_HospitalTillComponent`, `LF_HospitalCabinetComponent`; add a row to `PLACE_SOURCES` when another registrar gets a POI row). `tools/map/lib/overlay.mjs` joins them to the kind rows (core `LF_MapPois.conf` then the pack's `LF_MapPois*.conf`, replaced by kind), `visible(poi, persona)` from `tools/map/rules/visibility.mjs` decides what shows, and a place whose live state the header does not list stays dark (`--live-states 1,2` overrides the header's `m_aLF_LiveStates`). A world other than `main` draws on a plain metre grid and fits the view to its places (`--place fit`; `--base everon` keeps the terrain). With no place carrying a POI kind (the pack island has none yet) the render says so on stderr and draws no POIs, `overlay=none`. The stand-in rows are only `--fixture` and the render selftest. Tested by `tools/validation/map-places-selftest.mjs` (fixture layer `tools/map/render/fixtures/places.fixture.layer`: three kinds across the personas, a dark place, a kind with no row, a prefab-inherited place, a group, a nested child). Nested children are placed from the parent's coordinates turned by its yaw; entity ids and layer overrides beyond that are not modelled.
- ✅ **Session harness and `map-shots` (#2228, M0b):** the harness verb `map open|close|pan <x> <z> <zoom>|status` (`Feature/Map/LF_MapHarness.c`, a `modded class LF_AgentHarnessVerbs`, client side). The harness `input` verb refuses `GadgetMap`, so `open` holds the carried paper map (`SCR_MapGadgetComponent`, the way `hold PaperMap_01_folded` does; with none carried it opens the same `MapMenu` the gadget opens) and `close` switches the gadget's map mode off. `pan` centres on world `x z` with `SCR_MapEntity.ZoomPanSmooth` at the emulator's zoom: the view is `map width / 2^zoom` metres across (the width comes from the map entity, no constant), so a `tools\cli map render --zoom N` picture and the game frame the same ground. The map takes a few frames to start up and a pan before then does nothing, so `status` (`open=1 ppu=.. min=.. max=.. cx=.. cz=.. view_m=..`) is the read-back. The proof `node agent-box/session.mjs map-shots [--out dir] [--place name] [--bbox x0,z0,x1,z1] [--zoom N]` (`agent-box/proofs/map-shots.mjs`) takes its views from the emulator's own `resolveView` (default: the island, Saint-Philippe, the square), pans until the real width is within 5% of the emulator's, photographs the UI and writes `<view>.png` and `<view>-emulator.png`. Final proofs only (one run at the end of a visual card, `up --mission everon --profile full`); iterate in the emulator and the LOGIC tests.
