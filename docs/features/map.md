# The Everon map (epic #2223)

Design: `docs/architecture/everon-map.md`. One row per card; each card appends its own.

- ✅ **POI data (#2230, M2):** a point of interest is a live `LF_Places` entry whose kind has a row in the POI table. `Configs/Map/LF_MapPois.conf` (`LF_MapPoiConfig`, one `LF_MapPoiKind` row per kind: category, icon, label key, min zoom, visibility `PUBLIC`/`DISCOVER`/`HIDDEN`/`ROLE`, role) ships neutral rows; the pack overlays it by kind through `LF_ConfigOverlay` (`LF_Everon1989/Configs/Map/LF_MapPois_Everon1989.conf`, listed in the mission header, adds the hidden `Fence` kind). `LF_MapPois.CollectLive(audience, out)` reads `LF_Places` on any machine and applies the visibility rule (`LF_MapPoiRules.Resolve`) for an audience (`LF_MapPoiAudience`: roles held and what the player knows of each place id). Result per place: `hidden`, `faded` (heard of), `full`, or `pencil` (a hidden place the player met, never public). A kind with no row never shows (a vault, a dispatch source). The rule is one case table, `Configs/Map/Rules/visibility.cases.json` (the loader format of `tools/map/rules/index.mjs`), run by `LF_Test_MapPois` (Enforce; the engine cannot open a loose addon `.json`, so it reads `LF_MapPoiCases.generated.c`, written by `node tools/map/rules/visibility.mjs --gen`) and by `tools/validation/map-visibility-selftest.mjs` (node twin `tools/map/rules/visibility.mjs`, which also exports the emulator's `visible(poi, persona)`), so they cannot drift. Not done: drawing the icons (M4), the per-player known set and its saving (M13), the role source (on-duty police and medic) fed into the audience.
- 🧪 **Discovery core (#2241, M13):** what each character knows of each place: unknown, heard of or visited (D-M4), per character only (D-M12), saved as the `mapknown` payload (save version 42) and kept across the 24 h reset. `LF_MapKnown` (`Feature/Map/LF_MapKnown.c`) is the server store. The owner's machine looks around every 2 s (`LF_MapKnownScan`, not from a vehicle above 60 km/h) and asks `RpcAsk_LF_MapDiscover(kind, placeId)` on its own controller for a `DISCOVER` place within 20 m it has not visited; the server checks the kind is a `DISCOVER` POI row, the place is live, its own view of the character is within 20 m plus 10 m slack, and 5 asks a minute, then records the visit and answers `RpcDo_LF_MapKnown`. The board, the clerk and quests call `LF_MapKnown.Hear(playerId, placeId)` (never lowers visited; works for a place not live yet). On join, respawn and character switch the owner pulls the character's whole set (`RpcAsk_LF_MapKnownSync`, answered by one owner RPC of ids and states); `LF_MapKnown.FillAudience` hands the local set to `LF_MapPois`. The rule is one case table, `Configs/Map/Rules/discovery.cases.json`, run by `LF_Test_MapKnown` (through `LF_MapKnownCases.generated.c`) and by `node tools/map/rules/discovery.mjs` (the node twin; `known(poi, persona)` for the emulator's `--as known`). Not done: a per-kind discovery radius on the POI row (the rule takes it), callers of `Hear` (board, clerk, quests), drawing (M4). Tests `map/known`, `map/known-persist`.
- ✅ **Map plumbing (#2229, M1):** the Roleplay game mode (`GameMode_Roleplay.et`) now carries `SCR_MapConfigComponent` (gadget config `Configs/Map/LF_MapFullscreen.conf`) and `SCR_MapMarkerManagerComponent` (marker config `Configs/Map/LF_MapMarkerConfig.conf`), the two components vanilla's `GameMode_Base.et` has and ours lacked: without them the map menu returned before setup and no marker showed. `LF_MapFullscreen.conf` is a copy of vanilla's `MapFullscreen.conf` (an inherited array cannot drop items; a child config only adds) that keeps vanilla's layers, props, cursor module, descriptor visibility (town names and roads) and the map tools, markers, pencil, compass, ruler, watch, weather, light and radial, and drops the Conflict UI (`SCR_MapCampaignUI`), task list, journal (needs the task list and briefing) and military debug icons. `LF_MapMarkerConfig.conf` is vanilla's marker set (text, placed, military) without the dynamic squad-leader and air-support entries: their `InitServerLogic` reads `SCR_GroupsManagerComponent`, which this game mode has not, and crashed the manager's `EOnInit`. Test `LF_Test_MapConfig` (WORLD). Not done: the in-game picture of the open map (card M0b's `map-shots` proof is still owed), a `SCR_MapMarkerEntryMilitary` menu check in a live session.
- ✅ **Emulator POIs from live places (follow-up to #2251):** `tools\cli map render` draws the POIs a persona would see from the same data the game uses. The POI table is per kind with no coordinates (rule 9), so `tools/map/lib/places.mjs` reads the `.layer` files of `--world` (`main` the pack island, the default; `town` the DebugWorld village plus the pack's Everon1989Town layers; `debug`; `grid`; or a layers folder or one `.layer`), follows prefab ancestry for components a prefab carries, and collects each place's kind, id, position and live state from `LF_PlaceComponent` and the feature components that register a POI kind (`LF_WorkplaceComponent`, `LF_HospitalTillComponent`, `LF_HospitalCabinetComponent`; add a row to `PLACE_SOURCES` when another registrar gets a POI row). `tools/map/lib/overlay.mjs` joins them to the kind rows (core `LF_MapPois.conf` then the pack's `LF_MapPois*.conf`, replaced by kind), `visible(poi, persona)` from `tools/map/rules/visibility.mjs` decides what shows, and a place whose live state the header does not list stays dark (`--live-states 1,2` overrides the header's `m_aLF_LiveStates`). A world other than `main` draws on a plain metre grid and fits the view to its places (`--place fit`; `--base everon` keeps the terrain). With no place carrying a POI kind (the pack island has none yet) the render says so on stderr and draws no POIs, `overlay=none`. The stand-in rows are only `--fixture` and the render selftest. Tested by `tools/validation/map-places-selftest.mjs` (fixture layer `tools/map/render/fixtures/places.fixture.layer`: three kinds across the personas, a dark place, a kind with no row, a prefab-inherited place, a group, a nested child). Nested children are placed from the parent's coordinates turned by its yaw; entity ids and layer overrides beyond that are not modelled.
- ✅ **Waypoint on the map (#2235, M7):** `LF_MapWaypointUI` (`Feature/Map/LF_MapWaypointUI.c`, a `SCR_MapUIBaseComponent` listed in `LF_MapFullscreen.conf`) listens for `MapContextualMenu` (right mouse button, gamepad x) while the map is open, turns the cursor into a world position (`SCR_MapEntity.ScreenToWorldNoFlip`, height from the surface) and calls `LF_MapWaypoint.SetFromMap`, which marks `LF_Waypoint` with the id `map`. A second click moves the mark (`LF_Waypoint.Mark` on the same id would clear it, so the move is a clear and a mark); a click over a town board waypoint replaces it, since there is one waypoint. The waypoint, whoever set it, is drawn by a full-size `CanvasWidget` under the map root as a graphite pencil circle with a cross (`LF_MapWaypoint.BuildMark`: 24 ring segments and two strokes, a fixed 14 units at every zoom), redrawn on pan, zoom and when the board or an arrival changes it. The HUD marker over the target stays the only GPS-like aid (D-M9): no route line, no bearing line. Label key `LF-MapWaypoint_Label`. Test `LF_Test_MapWaypoint` (LOGIC). Not done: the hover card's "Set waypoint" (M4), the in-game picture (M0b `map-shots`), the bearing line from a player who knows where they are (D-M2).
- ✅ **Area conf rows (#2233 split M5b, Refs #2223):** `Configs/Map/LF_MapAreas.conf` (`LF_MapAreaConfig`, `Feature/Map/LF_MapAreaConfig.c`) holds `LF_MapAreaRow` rows (`m_sId`, `m_sLabel`, `m_eStyle`, `m_eShape` POLYGON or CIRCLE, `m_vCentre`, `m_fRadius`, `m_aPoints`) and is layered with each pack overlay by id through `LF_ConfigOverlay`, like the POI table. Core ships it empty (core holds no coordinate); the pack's `LF_Everon1989/Configs/Map/LF_MapAreas_Everon1989.conf`, listed in the mission header, adds Saint-Philippe's town line (a polygon round the dossier's buildings, 20 m out) and the safe square (40 m round the town hall). The pack file is generated from `docs/everon/places/saint-philippe/dossier.json` by `node tools/map/areas-from-dossier.mjs` (no typed coordinates; the selftest fails when it is stale). `LF_MapAreas.Collect` appends the rows after the zones and the layer entities, and a name already in the list is not drawn twice, so a `LF_ZoneComponent` entity named like a row stays the rule and the row is only its picture until the arrival slot (M19) places the real entities. A row with no outline (a polygon under three points, a circle with no radius) is skipped and logged. No lawless row until M7 (D4). `tools\cli map render --place saint-philippe` now draws `areas=2`. Tested by `LF_Test_MapAreaConf` (core: the empty core file, the rows becoming areas, the skips and the name dedupe), `LF_Test_EveronMapAreas` (pack: the header lists the overlay, the two rows merge in, the map collects them) and `tools/validation/map-area-conf-selftest.mjs` (the emulator reads the same files, layering, `m_sOp`, the multi-line array form). Not done: box and corridor shapes in a row (`LF_MapAreaShape` has POLYGON and CIRCLE only), the drawing (M6).
- 🟡 **World of Everon "Live now" and the spoiler check (#2211, X1 of #2201):** the website page `/docs/world-of-everon` gets a generated `## Live now` section (`website/scripts/live-now.mjs`, called by `build-content.mjs`, placed before the page's contents list). It reads the flagship header's `m_aLF_LiveStates` and each `docs/everon/places/<slug>/` dossier: a place is shown when its `mapping.json` has a `state` the header lists, with one overview picture (the `wide` one, else the first; copied to git-ignored `website/public/everon-live/`), its caption and one line (`mapping.line`, else the dossier's building counts). The page is stricter than the game: an empty or missing list shows nothing, not every state (D4). `tools/validation/validate-public-bible.mjs` fails when any page the site renders or `website/content/**` names `world-bible-internal.md`, or when `docs/everon/world-bible.md`, a dossier picture caption or the generated section contains a term from the `## Spoiler terms` list in the internal file (a missing list also fails). Proof: `tools/validation/public-bible-selftest.mjs` over `tools/validation/fixtures/public-bible/`. Nothing is live yet (the pack header lists no state, no mapping has a `state`), so the page is unchanged today.
- ✅ **Area layer (#2234, M6, Refs #2223):** `LF_MapAreasUI` (`Feature/Map/LF_MapAreasUI.c`, a `SCR_MapUIBaseComponent` listed in `Configs/Map/LF_MapFullscreen.conf`) owns one canvas over the map and draws every area `LF_MapAreas.Collect` returns: a wash or hatch fill (`PolygonDrawCommand`; the core white-ink `LF_MapHatch_Diagonal`/`Cross` tiles tinted by the style colour), an outline (`LineDrawCommand`: solid is one closed line; `dash` and `heavy-dash` are cut into dash polylines in screen pixels, so a lower zoom has fewer dashes; a huge outline needing over 400 dashes falls back to solid) and, from 0.3 px per metre up, a centred label (the style's `#LF-Map_Area*` key, or the area's own). It rebuilds on map open, pan end and zoom end; during a drag the canvas is only moved by the pan since the last build. The drawing rules are pure: `LF_MapAreasDraw.Build(area, screenOutline, ppu, viewW, viewH, themeTokens, label, out records)` returns `LF_MapAreaCmd` records (FILL, OUTLINE, LABEL) and culls an area off the canvas or under 4 px. Colours are the theme's `map-area-<style>-fill|line` tokens: `LF_UIThemeRecord.m_sMapTokens` ("name=#RRGGBB;..."), set on the paper record of `Configs/UI/LF_UITheme.conf`; a pack patches it (a name it leaves out keeps the built-in in `LF_MapAreasDraw.BuiltInHex`). Tested by `LF_Test_MapAreasDraw` (LOGIC: the records for a circle safe zone at two zooms, the lawless hatch and heavy dash, the town line, gated cross hatch, the cull and the theme tokens). Not done: the in-game `map-shots` proof (waits on M0b #2228), the event style's timer label (M15), pack-inked hatches (`LF_MapIcons_Everon1989_Hatch*.edds.meta` has no path in its `Name`, see the PR).
