# The Everon map (epic #2223)

Design: `docs/architecture/everon-map.md`. One row per card; each card appends its own.

- ✅ **POI data (#2230, M2):** a point of interest is a live `LF_Places` entry whose kind has a row in the POI table. `Configs/Map/LF_MapPois.conf` (`LF_MapPoiConfig`, one `LF_MapPoiKind` row per kind: category, icon, label key, min zoom, visibility `PUBLIC`/`DISCOVER`/`HIDDEN`/`ROLE`, role) ships neutral rows; the pack overlays it by kind through `LF_ConfigOverlay` (`LF_Everon1989/Configs/Map/LF_MapPois_Everon1989.conf`, listed in the mission header, adds the hidden `Fence` kind). `LF_MapPois.CollectLive(audience, out)` reads `LF_Places` on any machine and applies the visibility rule (`LF_MapPoiRules.Resolve`) for an audience (`LF_MapPoiAudience`: roles held and what the player knows of each place id). Result per place: `hidden`, `faded` (heard of), `full`, or `pencil` (a hidden place the player met, never public). A kind with no row never shows (a vault, a dispatch source). The rule is one case table, `Configs/Map/Rules/visibility.cases.json` (the loader format of `tools/map/rules/index.mjs`), run by `LF_Test_MapPois` (Enforce; the engine cannot open a loose addon `.json`, so it reads `LF_MapPoiCases.generated.c`, written by `node tools/map/rules/visibility.mjs --gen`) and by `tools/validation/map-visibility-selftest.mjs` (node twin `tools/map/rules/visibility.mjs`, which also exports the emulator's `visible(poi, persona)`), so they cannot drift. Not done: drawing the icons (M4), the per-player known set and its saving (M13). **Fixed (2026-11-17 map review, LOGIC `map/poi-role-audience`):** neither client audience builder added a role, so a `ROLE` kind (the police armoury) never showed, even on duty; `LF_MapPoiAudience.Local()` now adds the on-duty services from the replicated account state (`AddRolesFromState`). Since #2492 a client holds only public places; the server decides the private ones (row below).
- 🧪 **Discovery core (#2241, M13):** what each character knows of each place: unknown, heard of or visited (D-M4), per character only (D-M12), saved as the `mapknown` payload (save version 42) and kept across the 24 h reset. `LF_MapKnown` (`Feature/Map/LF_MapKnown.c`) is the server store. The server looks around every 2 s (`LF_MapDiscoverScan`, since #2492; it was the client's scan and `RpcAsk_LF_MapDiscover`, which needed every undiscovered place's position on the client): each player not in a vehicle above 60 km/h who stands within 20 m of a live `DISCOVER` place their character has not visited visits it (`LF_MapKnown.VisitServer`), and gets `RpcDo_LF_MapKnown` plus their private places. The board, the clerk and quests call `LF_MapKnown.Hear(playerId, placeId)` (never lowers visited; works for a place not live yet). On join, respawn and character switch the owner pulls the character's whole set (`RpcAsk_LF_MapKnownSync`, answered by one owner RPC of ids and states; its own gate `LF_MapKnownSync.Admit`, one answer a second per player with a second ask inside it deferred, never the shared `COMMS` rate bucket, which dropped the sync after three chess moves or board reads); `LF_MapKnown.FillAudience` hands the local set to `LF_MapPois`. The rule is one case table, `Configs/Map/Rules/discovery.cases.json`, run by `LF_Test_MapKnown` (through `LF_MapKnownCases.generated.c`) and by `node tools/map/rules/discovery.mjs` (the node twin; `known(poi, persona)` for the emulator's `--as known`). Not done: a per-kind discovery radius on the POI row (the rule takes it), callers of `Hear` (board, clerk, quests), drawing (M4). Tests `map/known`, `map/known-persist`, `map/known-sync-gate`.
- 🧪 **Private places are the server's (#2492, map review 2026-11-17 finding 5, D-M5):** a POI kind whose row is not `PUBLIC` (`DISCOVER`, `ROLE`, `HIDDEN`, e.g. the pack's `Fence`) is server-only. `LF_Places.RegisterOn(kind, id, entity, server)` refuses it on a client (`LF_Places.IsServerOnlyKind`, answered by the map's modded `LF_Places` in `Feature/Map/LF_MapPrivatePlaces.c`; logs `kept off this client`), so a modified client has neither the id nor the position of a place it may not see. The server sends each player, by one owner RPC on their own controller (`RpcDo_LF_MapPrivate`: kinds, ids, positions as decimetre ints; at most 512), the private places the visibility rule gives that player (`LF_MapPrivatePlaces.Entitled`: a discover place heard of or visited, a hidden place met, a role place while on duty), and sends it again on the join sync (join, respawn, character switch: a late joiner gets only their own set), on every heard-of or visited place, and when the police or medic duty bit of their account state changes (a modded `SCR_ChimeraCharacter.LF_SetAccountState`). Nothing private is broadcast. The client map draws its public `LF_Places` places plus that set (`LF_MapPois.GatherVisible`); a listen host draws through the same set. There is no org-gated POI row; an org shares a place by hand as an org mark. Cost (`perf/map-128`, this PC): the scan of 128 players over 400 places 0.3 ms a pass (budget 2 ms, every 2 s), one private set 0.25 ms (budget 1 ms). A world-layer entity still exists on every client; a truly secret place should carry no map-visible component in a replicated layer. Tests `map/private-registry` (WORLD), `map/private-entitled` (LOGIC).
- 🧪 **Personal marks saved (#2236, M8):** vanilla shared markers are off (D-M7): a modded `SCR_MapMarkerSyncComponent` forces its placed-marker limit to 0 after `OnPostInit` (the server's `RPC_AskAddStaticMarker` adds nothing) and refuses the client ask, and a modded `SCR_MapMarkerManagerComponent.InsertStaticMarker` turns every player add into a local one (the dialog, the quick menu and a drag all end there; server markers pass). The placed-marker dialog offers the pencil set from `LF_MapIcons.imageset` (cross, circle, arrow, note, question; `Configs/Map/LF_MapMarkerConfig.conf`; saved marks keep the icon by index, so the list only grows at the end). Each character keeps up to 20 marks (D-M11; the client refuses the 21st, the server refuses it again), saved as the `mapmarks` payload (save version 43) and kept across the 24 h reset. The owner uploads its whole list 2 s after a change (`RpcAsk_LF_MapMarksSet`, flat ints and notes, checked for shape and cap) and on join, respawn and character switch pulls it back (`RpcAsk_LF_MapMarksSync` → `RpcDo_LF_MapMarksSync`), re-inserting the marks as local markers (`Feature/Map/LF_MapMarks.c`, `LF_MapMarksSync.c`). Test `map/marks-persist`. Off-screen marks count: the marker manager moves a marker off the shown frame into its disabled list each map frame, so `LF_MapMarksClient.CollectPersonal` reads both lists for the 20-mark cap, the upload and the restore (before the map proof pass an off-screen mark was not counted and was dropped from the next upload; `LF_Test_MapMarksOffscreen`). **Fixed (2026-11-17 map review):** a shared mark (dispatch, org, job, event) is a local `PLACED_CUSTOM` marker too and was counted as personal: it took a slot of the 20 cap (a full map got no dispatch or org marks) and was uploaded and saved as the player's own mark, so it outlived leaving the org or going off duty. `IsPersonal` now skips read-only markers (`CanBeRemovedByOwner` false, which the share channel sets; LOGIC `map/share-not-personal`). The sync and save have their own rate bucket (`LF_ERequestKind.MAP`, 4 per 5 s), not the shared `COMMS` one that dropped a respawn's restore after three phone or board asks (LOGIC `map/marks-rate-bucket`). **Fixed (#2546):** a character switch inside the 2 s upload window saved the old character's list under the new character's key. The owner now drops a queued upload when its controlled entity changes, and every restore carries a session-only generation (`LF_MapMarks.IssueGeneration`) that the upload echoes on `RpcAsk_LF_MapMarksSet`; the server saves only a list stamped with the player's current generation and issued for the same character key, and drops anything else with a `[LFDebug:MapMarks] mark list dropped` line (`LF_MapMarks.SetFromPlayer`; LOGIC `map/marks-upload-generation`). No save-format change. **Fixed (#2623):** lists saved before the share fix still held copies of org and dispatch marks, which came back as ordinary deletable marks. The spawn restore (`LF_MapMarks.ExportCharacter`) now drops each saved mark that matches a live share the character sees (same text, or the share key as the client translated it, within 1 m), logs `[LFDebug:MapMarks] restore dropped N saved copy(ies)` and keeps the cleaned list for the next save. A copy of a dispatch mark whose share already expired cannot be matched and stays (alpha wipes clear it). WORLD `map/marks-drop-share-copies`. No save-format change.

- ✅ **Emulator POIs from live places (follow-up to #2251):** `tools\cli map render` draws the POIs a persona would see from the same data the game uses. The POI table is per kind with no coordinates (rule 9), so `tools/map/lib/places.mjs` reads the `.layer` files of `--world` (`main` the pack island, the default; `town` the DebugWorld village plus the pack's Everon1989Town layers; `debug`; `grid`; or a layers folder or one `.layer`), follows prefab ancestry for components a prefab carries, and collects each place's kind, id, position and live state from `LF_PlaceComponent` and the feature components that register a POI kind (`LF_WorkplaceComponent`, `LF_HospitalTillComponent`, `LF_HospitalCabinetComponent`; add a row to `PLACE_SOURCES` when another registrar gets a POI row). `tools/map/lib/overlay.mjs` joins them to the kind rows (core `LF_MapPois.conf` then the pack's `LF_MapPois*.conf`, replaced by kind), `visible(poi, persona)` from `tools/map/rules/visibility.mjs` decides what shows, and a place whose live state the header does not list stays dark (`--live-states 1,2` overrides the header's `m_aLF_LiveStates`). A world other than `main` draws on a plain metre grid and fits the view to its places (`--place fit`; `--base everon` keeps the terrain). With no place carrying a POI kind (the pack island has none yet) the render says so on stderr and draws no POIs, `overlay=none`. The stand-in rows are only `--fixture` and the render selftest. Tested by `tools/validation/map-places-selftest.mjs` (fixture layer `tools/map/render/fixtures/places.fixture.layer`: three kinds across the personas, a dark place, a kind with no row, a prefab-inherited place, a group, a nested child). Nested children are placed from the parent's coordinates turned by its yaw; entity ids and layer overrides beyond that are not modelled.
- ✅ **Session harness and `map-shots` (#2228, M0b):** the harness verb `map open|close|pan <x> <z> <zoom> [seconds]|status`, plus `map waypoint <x> <z>` (what a right-click does, `LF_MapWaypoint.SetFromMap`), `map mark <x> <z> [n]` (n personal marks through `InsertStaticMarker`, answering the count before and after, so the 21st refusal reads back) and `map probe` (the `-lfMapPlacesProbe` measurement on demand plus the mean frame ms since the map opened, sampled by `LF_MapPlacesUI.Update`) from the map proof pass (`Feature/Map/LF_MapHarness.c`, a `modded class LF_AgentHarnessVerbs`, client side). - ✅ **Share core (#2237, M9):** one server table, `LF_MapShares`, holds shared marks by the owning system's key (`LF_MapShareRow`: key, audience `PLAYER`/`ROLE`/`ORG`/`EVERYONE` and its id, x and z in metres, icon and colour indexes, text of at most 32 characters, expiry in world seconds or 0, and an optional area: a radius of 1 to 5000 m and an `LF_MapAreaStyle` id, radius 0 meaning none). `Put` sends a row to exactly its audience and takes it from players who held it but are outside a changed audience; `Remove` takes it from everyone who holds it. Audience resolution (`LF_MapShareRules.InAudience`): `PLAYER` is the active character's record key (`LF_Utils.GetPlayerUID`; the org is still looked up by character id), `ROLE` is an on-duty service only (`police` to police on duty, `medic` to medics on duty, off duty sees nothing: D-M10), `ORG` the org id, and an empty id or unknown audience reaches nobody. Membership changes go through `Refresh(playerId)` (owners call it at once; a sweep every 5 s refreshes everyone and expires rows, spread over 20 ticks of 250 ms since #2531), which sends the diff: rows the player now belongs to and removals for the ones they left. `LF_OnPlayerSpawnedEvent` (late join or respawn) clears the client's shared marks and resends the full set; a player holds at most 64 rows. Delivery is `LF_MapShareComponent` on `PlayerControllerRoleplayMP.et`: `RpcDo_MapShareAdd/Remove/Clear` with `RplRcver.Owner` on the recipient's own controller, never broadcast and no entity id on the wire; the client inserts each row as a local vanilla static marker (`InsertStaticMarker(marker, true)`) the player cannot delete (D-M7: the vanilla networked marker path is not used). A row's area rides the same `RpcDo_MapShareAdd` (radius and style appended): `LF_MapShareAreas.Show` registers a local circle in `LF_MapAreas` named after the row's key (the row's text is its label), `Hide` takes it off with the mark (remove, replace, clear before a resend), so a late joiner or respawn gets it back through the resend; `Put` drops an area that is not drawable (`LF_MapShareRules.AreaValid`) and still sends the mark. Test `map/share-areas` (LOGIC). Rules (audience, expiry, diff, area validity) are one case table, `Configs/Map/Rules/shares.cases.json`, run by `LF_Test_MapShares` (LOGIC, via `LF_MapShareCases.generated.c` from `node tools/map/rules/shares.mjs --gen`, plus a four-player fixture through the table with a recording sink) and by `tools/validation/map-shares-selftest.mjs` (node twin `tools/map/rules/shares.mjs`). Nothing is saved (owners re-issue rows; org marks are M12). Not done: the callers (dispatch M10, taxi and jobs M11, org marks M12, events M15) and the shared-mark icon config.
- 🧪 **Org marks (#2240, M12):** a member whose rank holds the `MANAGE_TERRITORY` right (founders have it; a founder gives it to officers through the rank rights) places a mark for the whole organization, at most 20 per organization (D-M11). `LF_OrgMapMarks` (`Feature/Organizations/LF_OrgMapMarks.c`) is the server store; each mark is an `ORG <orgId>` row of `LF_MapShares` keyed `org:<orgId>:<serial>`, so members get it and nobody else does. The client asks on its own controller with `LF_MapShareComponent.AskOrgMark(x, z, icon, colour, text)` (`RpcAsk_OrgMark`) or `AskOrgMarkRemove(key)`; the server checks the organization, the right, the cap, one add per 2 s per character, int16 positions and u8 icon and colour, and trims the text to 32 characters (no profanity filter yet). Serials are never reused in a session (a per-org high-water mark), leading `#` is stripped so player text is never a string table key. A load keeps the marks of an organization that is not registered at that moment (a whole-store re-apply may run mid-swap); a future disband path must remove its org's marks. Saved as the `orgmarks` payload (save version 44), kept across the 24 h reset; a load re-puts every mark into the share table and skips rows with no org, repeated keys and rows past the cap. Joining or leaving an organization (create, invite, kick, leave) calls `LF_MapShares.Refresh` for that player at once (`LF_OrgMapMarks.RefreshCharacter`). This is how an org shares an underworld place by hand (D-M5). Org marks are put at load, so they take up to 20 of a player's 64 share slots ahead of later rows. Not done: the map UI to place and remove org marks (the asks exist; the dialog is M8's), the shared-mark icon config, officers holding the right by default. Test `map/org-marks` (PERSISTENCE). **Fixed (2026-11-17 property review, LOGIC `map/org-marks-character-id`):** the asks and `RefreshCharacter` resolved the player with `LF_Utils.GetPlayerUID`, the record key, which for an account's first character is the account uid; organizations list members by character id, so that character's every add and remove was refused.
