### `LF_EventSceneWalk` — `Feature/Events/LF_EventSceneWalk.c` (#1956, 2026-11-17)
- ⚠️ Logic proven, real AI walk not yet seen in play: `Begin(crew)` resolves the plan's waypoints in order plus the scene target and, in a world with an AIWorld, spawns one vanilla `Group_Base` with an `AIWaypoint_Move` (completion radius 3 m) on every route point in order; each walker joins the group as its stagger spawns it (`ActivateAI`, `AddAgent`), so the formation walks them as a loose group. Progress is read from positions: a waypoint counts as passed within 3 m or once the walker is nearer the following point; a walker arrives only after passing every waypoint and coming within 3 m of the target. A walker with no progress along the route for 20 s, or still walking when the plan's walk timeout ends, times out (`[LFDebug:Events] ... timed out`) and is removed once no player sees it. Without an AIWorld nobody is driven (logged). One walk at a time; a world reset drops it. The scene operation (#2137, below) calls it after `LF_EventSceneSpawn.Start`. Tests: `events/scene-walk` (WORLD, grid cell `event-scene`, the test moves the walkers).

### `LF_EventShell`, `LF_OnEventPhase`, `LF_EventOperation` — `Feature/Events/LF_EventShell.c`, `LF_EventsEvents.c` (#1950, 2026-11-16)
- ✅ The server shell loads `Configs/Events/LF_Events.conf` at game start and ticks every event once a second on the call queue. A phase's `m_aModules` names condition, abort and operation modules registered by id (`LF_EventShell.RegisterCondition|RegisterAbort|RegisterOperation`); operations run in order at the phase's cadence and an acting one restarts the idle clock. An idle event starts when its first phase's conditions hold (they are the start gate), then `LF_EventPhaseRules` advances or ends it. An event runs only with `m_bEnabled` set: off by default, and the core `example` ships off, so a live server runs nothing until a pack patch or its own event turns one on. Events come from `LF_EventOverlay` (core plus pack overlays; a patch may set `m_bEnabled`). Each change logs `[LFDebug:Events] event <id> start|advance|end`, publishes `LF_OnEventPhase` (kind start/advance/end, reason done/abort/idle) and is broadcast to clients by RPC on the game mode (`LF_EventPhaseBoard.PhaseOf` on the client). An unregistered module id is logged once and holds the phase. Run state survives a restart by phase name (#1951, below); PLAYERS_NEARBY counts the players near the event place once one is bound (#2105, below); a late joiner gets the running phases from the JIP snapshot (#2106, below). Tests: `events/shell` (WORLD).

### `LF_EventPlace` — `Feature/Events/LF_EventPlace.c` (#2105, 2026-11-17)
- ✅ An event has a place: `LF_EventPlace.Bind(eventId, sceneId, radius)` names the scene whose `event_target` marker (#1954, found by component through `LF_Places`, never by coordinates) is its centre, with an optional per-phase radius (`BindPhaseRadius`). The shell counts the connected players within that radius on the server at each tick, so a `PLAYERS_NEARBY` condition can hold and a `NEARBY_BELOW` abort fires only when the place is empty. An event with no place, or whose marker is not placed, counts 0 and logs one `[LFDebug:Events]` warning. The binding is made in code by whoever owns the event; the event config has no place field yet. Tests: `events/players-nearby` (WORLD, grid cell `event-scene`).

### `LF_EventModuleLoader`, `LF_EventSceneOperation` — `Feature/Events/LF_EventModuleLoader.c` (#2137, 2026-11-17)
- ✅ An event config lists its modules in `m_aModules` (`LF_EventModuleRef`: an id and a `.conf`); a pack overlay adds its own and one with the same id replaces the earlier (logged). At game start the shell registers each by the `.conf`'s root class: `LF_EventPrecondition` (hour window, players online or nearby, cooldown) as a condition, `LF_EventAbort` as an abort, `LF_EventScene` as an `LF_EventSceneOperation`. A ref that does not load, has another root or a taken id is logged `[LFDebug:Events]` and skipped, so its phase holds. The scene operation stages its scene once per phase run: plans it against the free AI budget, spawns the walkers and starts their walk, then on its own ticker waits for the walk to end, the despawn delay, and no player in sight before removing them. While on stage it is busy (`LF_EventOperation.Busy`) and holds its phase, so the event ends only after the scene has left (or on the phase's idle timeout or an abort). A scene may name walker prefabs (`m_aPrefabs`, handed out in turn), which win over its role. Tests: `events/module-loader` (WORLD, grid cell `event-scene`).

### `LF_EventSceneHarness` — `Feature/Events/LF_EventSceneHarness.c` (#2173, 2026-11-16)
- ✅ A session can run an event that ships off. Harness `eventscene start <{GUID}fixture.conf> [hour]` (dev gate on the server) reloads the event list, lays the fixture (root `LF_EventsConfig`, the pack overlay rules, so it can turn `m_bEnabled` on and bring module refs) over it, hands it to the shell and the module loader and forces the shell's hour when one is given. `eventscene status [eventId]` answers the fixture, the event's phase and the running scene's crew (spawned, walking, arrived, timed out, seconds); `eventscene stop` puts the files' own list back and the real hour.
