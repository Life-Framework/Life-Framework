### `LF_EventWaypointComponent` — `Feature/Events/LF_EventWaypointComponent.c` (#1954, 2026-11-16)
- ⚠️ Markers only, no event runs on them yet: a placed scene marker with a scene id, a role (waypoint, spawn, target) and an order. It registers in `LF_Places` (`event_waypoint` and `event_spawn` as `<scene>#<order>`, `event_target` as `<scene>`), so an event names a scene by id and core holds no coordinates. `FindWaypoints` and `FindSpawns` return the scene's markers lowest order first (a gap keeps the order); `FindTarget` returns the one target. A marker with no scene id, or a negative order, is logged (`[LFDebug:Events]`) and not registered; a second marker with a taken order is refused by `LF_Places`. Prefabs `Prefabs/Systems/Events/LF_EventMarker_{Waypoint,Spawn,Target}.et`; test route `grid_event_scene` (four waypoints, two spawns, a target) in grid cell `event-scene`. ### `LF_EventSceneWalk` — `Feature/Events/LF_EventSceneWalk.c` (#1956, 2026-11-17)
- ⚠️ Logic proven, real AI walk not yet seen in play: `Begin(crew)` resolves the plan's waypoints in order plus the scene target and, in a world with an AIWorld, spawns one vanilla `Group_Base` with an `AIWaypoint_Move` (completion radius 3 m) on every route point in order; each walker joins the group as its stagger spawns it (`ActivateAI`, `AddAgent`), so the formation walks them as a loose group. Progress is read from positions: a waypoint counts as passed within 3 m or once the walker is nearer the following point; a walker arrives only after passing every waypoint and coming within 3 m of the target. A walker with no progress along the route for 20 s, or still walking when the plan's walk timeout ends, times out (`[LFDebug:Events] ... timed out`) and is removed once no player sees it. Without an AIWorld nobody is driven (logged). One walk at a time; a world reset drops it. Nothing calls `Begin` yet (the shell module, with `LF_EventSceneSpawn.Start`). Tests: `events/scene-walk` (WORLD, grid cell `event-scene`, the test moves the walkers).

### `LF_EventPrecondition`, `LF_EventAbort`, `LF_EventContext` — `Feature/Events/` (#1949, 2026-11-16)
- ✅ Condition modules (AND-ed) hold a phase until the in-game hour is in range (may wrap midnight), enough players are online or nearby, and a cooldown since the event last ended is over; abort modules (OR-ed) end the event on an hour window, too few players online or nearby, or a phase that lasts too long. Pure over a measured `LF_EventContext`; the shell (#757) fills it and feeds `LF_EventPhaseRules.Decide`. Tests: `events/preconditions` (LOGIC).

### `LF_EventShell`, `LF_OnEventPhase`, `LF_EventOperation` — `Feature/Events/LF_EventShell.c`, `LF_EventsEvents.c` (#1950, 2026-11-16)
- ✅ The server shell loads `Configs/Events/LF_Events.conf` at game start and ticks every event once a second on the call queue. A phase's `m_aModules` names condition, abort and operation modules registered by id (`LF_EventShell.RegisterCondition|RegisterAbort|RegisterOperation`); operations run in order at the phase's cadence and an acting one restarts the idle clock. An idle event starts when its first phase's conditions hold (they are the start gate), then `LF_EventPhaseRules` advances or ends it. An event runs only with `m_bEnabled` set: off by default, and the core `example` ships off, so a live server runs nothing until a pack patch or its own event turns one on. Events come from `LF_EventOverlay` (core plus pack overlays; a patch may set `m_bEnabled`). Each change logs `[LFDebug:Events] event <id> start|advance|end`, publishes `LF_OnEventPhase` (kind start/advance/end, reason done/abort/idle) and is broadcast to clients by RPC on the game mode (`LF_EventPhaseBoard.PhaseOf` on the client). An unregistered module id is logged once and holds the phase. Not yet: run state is not persisted (a restart starts every event idle), PLAYERS_NEARBY counts the players near the event place once one is bound (#2105, below), late joiners hear only the next change. Tests: `events/shell` (WORLD).

### `LF_EventPlace` — `Feature/Events/LF_EventPlace.c` (#2105, 2026-11-17)
- ✅ An event has a place: `LF_EventPlace.Bind(eventId, sceneId, radius)` names the scene whose `event_target` marker (#1954, found by component through `LF_Places`, never by coordinates) is its centre, with an optional per-phase radius (`BindPhaseRadius`). The shell counts the connected players within that radius on the server at each tick, so a `PLAYERS_NEARBY` condition can hold and a `NEARBY_BELOW` abort fires only when the place is empty. An event with no place, or whose marker is not placed, counts 0 and logs one `[LFDebug:Events]` warning. The binding is made in code by whoever owns the event; the event config has no place field yet. Tests: `events/players-nearby` (WORLD, grid cell `event-scene`).

### `LF_EventShellRow`, `worldevents` payload — `Feature/Events/LF_EventShellSave.c` (#1951, 2026-11-17)
- ⚠️ Events survive a restart by phase name: the `worldevents` payload (save version 41) keeps each event's phase name, phase age, cooldown left, time since it ended and an int bag (`LF_EventShell.GetInt/SetInt`, for module state), with times relative to the save because the shell clock restarts at 0. On load an event saved in a phase it still has goes to its full cooldown (a scene is never resumed), an idle one keeps its cooldown left, a phase name it no longer has loads idle with a warning, and an event id this boot does not run is dropped with a warning. Restart proof is manual (`wt e2e`). Tests: `events/shell-persist` (WORLD).
