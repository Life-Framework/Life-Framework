## Findings

**Real player-hitting game bugs: none.** No issue filed, no milestone touched.

1. **`export-crane-proof` fails on a thousands comma: a proof defect, the game paid right.** Step 4 reads the pay from the server line `export order handed in by <uid>: $1,040` with `/export order handed in by \S+: \$(\d+)/` (`agent-box/proofs/export-crane-proof.mjs:146`). `fdeb116d9` (money text, one formatter for every amount) made that line print `LF_MoneyFormat.FormatMoney(paid)`, so the regex captures `1` and the check `after === before + paid` reads "paid $1, cash 1633". The cash itself went from 593 to 1,633: the full $1,040 for 40 iron bars. The short count refused (`brought 39 of 40`), paid nothing, and the second hand-in paid nothing, as before. The fix is one character class, `\$([\d,]+)` and a `replace(/,/g, "")`; not applied here because this branch ships the doc only, and the proof can run once per session (the board's order is taken), so it was not rerun. **Saturday's run will hit it unless that line is fixed first.** Other proofs read money with the same `\$(\d+)` shape and would break the same way at $1,000 or more: `booking-desk-proof.mjs:213` (`fine=`), `drive-haul-proof.mjs:47`, `truck-haul-proof.mjs:63` and `lumber-arc.mjs:48` (`steady $N/h`, $753/h today), `harvest-island.mjs:44`. They passed here because their amounts are under $1,000.
2. **`drive-haul-proof` fails its three driven legs** (1a truck to a tree: stuck 23.3 m in 125.2 s; 2a the loaded truck back to the saw: stuck 34.8 m in 144.1 s, 20.3 m off the pad, 2 backups; 3a saw to the timber counter: stuck 34.7 m in 148.3 s, 187.2 m off the pad). **Harness limit**, the one from dry run 3, identical to dry run 5. Every economy step around the legs passes and `truck-haul-proof` (the same haul with the truck moved by the proof) passes 12 of 12 in the same session. The manual truck drive in "Manual testing" stays the only way to rule out a player-side problem.
3. **`downed-flow-proof` failed once on "Revive is listed after Introduce", then passed.** The proof reads the order of the `look` list (the engine's action collection order), not the menu a player sees (the menu sorts by `Sort Priority`; #5155 gave Revive -10). Run 1: the medic's `look` listed `... LF_IntroduceAction, LF_ShowIDAction, LF_GiveCashAction, LF_GiveItemAction, LF_ReviveAction`; the picture of that run shows the medic still looking at the clinic desk ("Clock out" is the focused row), so it says nothing about the displayed order. Run 2 (same session, `look` now starts with `LF_MedicCarPoolDrawAction` and lists `LF_ReviveAction` before the introduce rows): pass, with the HUD line counting `Bleeding out 3:00 ... 2:30 ... 2:15`, give-up and the respawn button. Both medic and patient stand at the clinic duty desk in this proof, so the collection order shifts with where the two characters spawn. Not filed: no repro of a wrong menu order, only of the proof's `look` proxy. If Saturday's run shows it red again, look at the picture of the medic facing the body (the 5155 evidence picture shows "Revive" as the first row) before calling it a game bug.
4. **The new proofs run clean on this head**: `map-search-proof`, `lot-sheet-proof`, `downed-call`, `clinic-bed-proof` and `crime-playtest-proof` all pass on the first run; the late joiner reads the plate now.
5. **`booking-desk-proof` passed its frame-gap check (`1f0`) on an idle box** (no sibling session running, 31 GB RAM free): dry run 5's 3616 ms was load, not a pay-time hitch. The watch item can be dropped.
