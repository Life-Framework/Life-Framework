## Findings

**Real player-hitting game bugs: none.** No issue filed, no milestone touched.

1. **`starter-gates-proof` after the flow fails on the same character** (proof order, not game). The page's step 1 reads "the first-two-hours flow, then `starter-gates-proof`", but the flow already ran the clerk talk (`quests=arrival_done,...`), and the clerk issues one ID card per account, so the proof's wait for `idcard=<set>` runs out (`the clerk did not hand over the ID card`). On a fresh account in a new session it passes (133.5 s). For Saturday: run `starter-gates-proof` on client 2 or in its own fresh session before the flow's clerk step, not after the flow on client 1. The page's step 1 should say so; not changed here (this branch writes the run doc only).
2. **`drive-haul-proof` fails its three driven legs** (1a truck to a tree: stuck 4 m in 70.5 s; 2a the loaded truck back to the saw: stuck 0 m in 66.4 s, 21.2 m off the pad, 6 backups; 3a saw to the timber counter: stuck 0 m in 66.5 s, `no_road_path`). Same as dry run 3, **harness limit**. The economy steps around the legs all pass (1b tree felled, 1c log loaded at the tailgate, 1d 6 logs 12/12 units, 2b 6 of 6 sawn, 2c +$180 at the woodlot buyers, 3b +$15 at the timber counter; **+$195 in 12.2 min, $961/h**), and `truck-haul-proof` (the same haul with the truck moved by the proof) passes 12 of 12 in the same session. The manual drive of a bought truck out of the woodlot yard, listed in dry run 3's "Manual testing", is still the only way to rule out a player-side problem.
3. **`session up` refused once for RAM** (`not enough free RAM ... close apps or retry with --wait`, exit 75 after 7 s) with two other agents' sessions up. The proof I then ran, with no session behind it, failed `B is wanted after the robbery: wanted=undefined`: a void result, not a finding. `up ... --wait` booted at once in 93 s. Saturday: check `pool status` before booting.
4. **`island-jail-breach-proof` was cut off once** by my own tool call dying mid-run (the log stops after "B is serving again"); the session was gone, so the run is void and it was repeated in a fresh session, where it passes (426.0 s). Run it in the background and wait on the process, as `truck-haul-proof` and the heist.

## Noticed (no issues)

- `ui-click-smoke` ran in session A on the flow's character; its default checkpoints that character to hour 10 and buys a row, so the hour 3 checkpoint right after it overwrote that. Worth knowing for Saturday: give it its own session or use `fresh`.
- `harness.mjs checkpoint <h>` is not a command (`harness: 'checkpoint' is not a harness command ... send checkpoint 3`); the working forms are `tools\cli checkpoint <h> --client <n>` or `harness.mjs --client <n> send checkpoint <h>`. The page does not name it.
- `t3_background_wait` returned at once for a running background task in this run (three times); `Wait-Process` on the proof's node pid blocked as expected.
- `starter-gates-proof` and `ui-click-smoke` both reach `WelcomeGuideCloseButton` `widget_not_found` retries after guide close; harmless.
